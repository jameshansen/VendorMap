VendorMap · UI concepts · Sept 2026

Three boxes, five screens

Interface sketches for the split architecture: a Manager that deploys events, an Event box that runs one market and is then thrown away, and an Accounts service that remembers vendors across all of them. The written spec lives in ARCHITECTURE-PROPOSAL.md; this is only what it looks like.

Manager Event Accounts

1. Every market, past and future

Manager

The organiser's home. Boxes, not events: each row is a separate deployment with its own database, and exactly one of them is serving the public booking address at any time. Nothing here can approve a vendor or move a table, and that separation is the point.

One address, always

jkepac.ca/booking serves whichever event is live, so the address on your posters never changes. Going live moves the outgoing market to its own /booking/past/… path and makes it read only. Nothing is deleted, and the flip can be reversed.

2. Staging next year's market

Manager

Creating an event means provisioning a container, a database and an API key. The organiser sees a form, not a terminal. Copying last year's floor plan is the step that saves the most work, and the one most likely to carry a bug forward if booked tables are not reset. Note that staging and going live are separate: this form never disturbs the market currently running.

What happens when you deploy

Creates the database, runs migrations, issues an Accounts API key scoped to this event and starts the container at /booking/preview/christmas-2027, visible only to you. Roughly 40 seconds.

It does not touch the market currently running. Set up the floor plan, check it over, then press Go live when you are ready: that is a separate step, it takes about a second, and it can be reversed.

3. Signing up for one specific market

Event

The vendor's view, after clicking the emailed verification link. The heading names the event because the application belongs to the event, not to VendorMap in general. Details arrive prefilled from Accounts, and the page is explicit about where they came from and that this is a fresh application.

5. One vendor, every market

Accounts

The ground truth record. It holds who a vendor is and what happened each time they applied, and nothing else. No approvals, no tables, no payments: those belong to the event box that created them. Written to by every box, owned by none of them.
